# Issue tracker: Hermes Kanban

Issues and specs for this repo are cards on the `default` board with tenant `portfolio`. Always pass `--board default`; the currently selected board may be `personal`. Use `--tenant portfolio` when creating or listing cards. Refer to cards by their full `t_...` ID, not GitHub issue numbers. GitHub Issues is not this repo's configured tracker.

## Conventions

- Create: `hermes kanban --board default create --tenant portfolio --body-file <path> "<title>"`. Use `--triage` for an issue needing evaluation. A card without `--triage` starts in `ready`; do not assign it to an agent until it is agent-ready. Put `**Status:**` and `**Type:**` markers in the body (see `triage-labels.md`).
- Read: `hermes kanban --board default show <id> --json` to include the body and comments.
- List: `hermes kanban --board default list --tenant portfolio --json`. Filter by `--status` as needed; add `--archived` when looking for closed cards. Verify the tenant on individually fetched cards too: `show` is board-scoped, not tenant-scoped.
- Comment: `hermes kanban --board default comment <id> "<text>"`. During triage, start each comment with `> *This was generated by AI during triage.*`.
- Edit title/body: `hermes kanban --board default edit <id> --title "<title>" --body "<entire updated body>"`. Preserve other body content when editing a role or category; for multiline content, pass the complete body from a safely quoted file/script, not a lossy shell literal.
- Assign to an agent only when agent-ready: `hermes kanban --board default assign <id> <profile>`. Check available profiles with `hermes kanban --board default assignees`.
- Dependencies: create with `--parent <blocker-id>` or link existing cards with `hermes kanban --board default link <blocker-id> <child-id>`. A child created with an unfinished parent stays in `todo` and becomes `ready` after its parents finish. `link` on an existing card does not demote it; check its column before assuming the edge prevents dispatch.
- Resolve completed work: `hermes kanban --board default complete <id> --summary "<verified outcome>"`.
- Close without implementation: comment with the reason, then `hermes kanban --board default archive <id>`. Archive is also used for other closed cards, so read the recorded triage role to distinguish `wontfix`.
- After every write, read the exact card back with `show <id> --json`.

There is no generic status setter. Read `docs/agents/triage-labels.md` for role-specific transitions. Never run `specify` over a carefully written brief merely to change columns.

## Pull requests as a triage surface

**PRs as a request surface: no.** External GitHub PRs are not automatically kanban cards. Handle them only if the user explicitly requests it.

## When a skill says "publish to the issue tracker"

Create a card on the `default` board with tenant `portfolio`. Put the full spec or ticket in its body, including `**Status:**` and `**Type:**` when applicable. For multiline bodies, write a scratch file first and pass `--body-file <path>` (or `--body-file -` for stdin). Create blocker cards before children; use native `--parent <blocker-id>` for each genuine blocker. A source card may be referenced in the new card's body without modifying the source.

## When a skill says "fetch the relevant ticket"

Use the full `t_...` ID with `show <id> --json`, and check that its tenant is `portfolio`. If the user gives an ambiguous number or a GitHub `#number`, ask for a kanban card ID rather than guessing.

## Wayfinding operations

The map is a card holding Notes / Decisions-so-far / Fog. Related tickets reference the map; record their `research` / `prototype` / `grilling` / `task` type in the body. **A `--parent <map-id>` edge blocks its child until the map is completed**, so do not make an active map the parent of live frontier tickets. Instead, put `Part of: <map-id>` in each ticket body and list the ticket IDs in the map. Create native `--parent <blocker-id>` edges only for true blockers, after creating blocker cards first. An active map is a grouping record, not a blocking prerequisite.

Find the frontier by listing tenant `portfolio` cards in `ready`, then filtering by map membership, parent completion, and assignee. Check each candidate with `show`. Claim by assigning it to the driving profile before starting work. Resolve with a comment containing the answer, `complete <id> --summary "<verified outcome>"`, then update the map's Decisions-so-far with a pointer to that card and answer.
